# Agent Instructions

This repository has project-specific Amazon template filling rules. Do not fill Amazon upload templates from general marketplace knowledge alone.

Before any task involving Amazon template filling, auto-fill, listing drafts, SKU route decisions, processing-summary fixes, or upload self-checks, read these files in this order:

1. `PROJECT_RULES.md`
2. `docs/amazon_template_fill_workflow.md`
3. `data/reference_docs/亚马逊上传表格_通用自检资料.md`
4. `app/template_writer.py`
5. `app/template_validator.py`
6. `app/success_rule_defaults.py`

Treat `app/template_writer.py` and `app/template_validator.py` as the source of truth for what is actually written and checked. Treat docs as workflow and policy guidance. If a task asks for current rules, inspect the code again instead of answering from memory.

When changing any persistent Amazon template filling default, validation rule, or reporting behavior, update this `AGENTS.md` summary in the same change so new Codex tasks do not start from stale defaults.

Current high-level defaults:

- Default route is `Haul Generic Variation` parent/child variation unless the user explicitly selects single-link or set-bundle.
- Parent SKU should use the base SKU directly; do not append `Parent`, `-Parent`, or similar parent labels unless the user explicitly provides that format.
- Fill `List Price` and Haul/BZR `our_price`; leave `minimum_seller_allowed_price` blank by default and do not default-fill `maximum_seller_allowed_price`.
- `Skip Offer` should remain blank.
- New item condition is `New`.
- Generic route uses `Brand = Generic` and `Manufacturer = Generic`.
- Parent variation rows intentionally leave `Manufacturer` blank; intake validation must not reject that blank Parent field. Child rows still require Manufacturer.
- The title self-check accepts lowercase `mm` as a measurement unit. The bead-specific listing draft copy in `app/analyzer.py` is written to the same title, five-bullet, and four-paragraph length rules as the formal self-check.
- For S1-to-S2 store-ops handoff, the listing workbench creates or reuses one local listing project per operations project ID, then reads the uploaded Amazon template's Valid Values to choose the exact variation theme spelling before generating and self-checking the upload file.
- Dimensions use `Inches`; package weight uses `Pounds`.
- Ordinary non-battery / non-dangerous goods products use `batteries_required = No`, `batteries_included = No`, and `supplier_declared_dg_hz_regulation = Not Applicable`.
- Filled Amazon upload files use Chinese product name plus variant/color plus version with no separator before the version label, for example `卷纸切割器黑色V1.xlsx`; corrected versions continue as `V2`, `V3`, etc.
- For `PLANTER`, fill conditionally required `Model Name`, `Special Features`, `Mounting Type`, and `Product Compliance Certificate`; clear non-applicable `item_length_width_height` fields when Amazon ignores them.
- For `PET_TOY`, fill conditionally required `Subject Character` on both Parent and Child rows; for ordinary cat toys use the product subject such as `Cat`. Backend error `99022` confirms that PET_TOY Parent rows also require item length, width, height, their units, and item weight/unit; fill these item measurements while keeping Parent package dimensions and package weight blank.
- Backend error `99022` confirms that `TOWEL` Parent rows require ready-to-use item length/width with units and item weight/unit, and `GIFT_WRAP` Parent rows require unit count/type and item weight/unit. Use actual ready-to-use towel dimensions from the task when available; keep Parent package measurements blank.
- For `GARLAND`, fill the child-row dynamic required fields `Model Name`, `Included Components`, and `Required Assembly`; after generating V1, open the workbook in a spreadsheet app so its conditional formatting recalculates, then fill any newly red required cells and overwrite the same V1 rather than creating V2.
- Backend error `99022` confirms that `EARRING` Child rows require Stone Creation Method and Stone Treatment Method when the stone group is present. For no-gemstone earrings, use the current template Valid Values `Unknown` and `Not Treated` respectively.
- Backend errors `90004200` and `90004205` confirm that apparel `Fabric Type` must include the actual composition percentage, and apparel sizes must use the current template's exact dependent enum. For SHORTS with `US + Male + Adult + Alpha`, use `Medium` instead of `M` and `XX-Large (xx_l)` instead of `2XL`. For UNDERPANTS with `US + Female + Adult + Alpha`, use full values such as `Small`, `Medium`, `Large`, `X-Large`, and `XX-Large (xx_l)` instead of abbreviations. Non-range sizes keep the corresponding Size To Range field blank.
- Backend error `99022` confirms that `BRACELET` Parent rows require Item Length End to End, Item Weight, and all three Item Dimensions values (length, width, and height). Keep their existing units paired with the values; Parent package dimensions and package weight remain blank.
- For `SPORT_RACKET`, fill sport-racket conditionally required defaults for racket grip/overgrip items, including Department Name, Style, Material, Frame Material, Pattern, Skill Level, Unit Count, Included Components, Sport Type, Grip Size, Grip Type, Hand Orientation, Racket Performance Specialty, Import Designation, Warranty Description, item/package weight, package dimensions, batteries, and dangerous goods fields; do not broadly fill unrelated conditional fields such as battery chemistry, SDS, California Proposition 65, or government contract fields for ordinary non-battery grip tape. For ordinary grip tape with no warranty promise, use `Warranty Description = No Warranty`.
- When a jewelry template's `metals` group includes Metal Weight Unit, the value must match that Product Type's current template `Valid Values` exactly. For the current `APPAREL_PIN` template, the only accepted Metal Weight Unit is `Grams`; do not reuse the project's default `Pounds` package/item-weight unit in this metal-specific field.
- Controlled enum fields must match the template `Valid Values` exactly, including case and slash formatting. Check fields such as `variation_theme#1.name`, `parentage_level`, and relationship type against the current template before delivery; for example, a PET_TOY template may require `COLOR`, not `Color`.
- Variation theme choices must consider buyer-facing display, not only upload validity. Per Amazon Seller Central help `G7UJDST28Q5Y7PWY`, variation dimensions are customer choices; visual dimensions such as color/pattern can affect images, non-visual dimensions such as size usually do not, most non-apparel categories show the best-selling child by default, and child order is Amazon-controlled. When the desired customer option is one combined label like style plus size, prefer a supported single text dimension such as `SET_NAME` and write values like `WARNING Print 1.97 in x 118.11 in`; use combined dimensions like `SIZE/SET_NAME` only when separate customer selectors are intended.
- Title self-checks now enforce Amazon-facing character and structure risks in addition to the project 100-125 character target: block prohibited/decorative characters, repeated punctuation, HTML/noise, promotional or logistics claims, medical/cleaning/protection result claims, ingestion wording such as `Flavor`, absolute ingredient claims such as `Natural`, and sensitive material/compliance claims such as `Food Grade`, `BPA Free`, or `Eco Friendly` in titles. Use `Scent` for non-food scent attributes. Ordinary verifiable materials such as `Velvet`, `Plastic`, or `Silicone` may appear in titles when useful.
- Generic listing copy must not retain competitor brands. Backend error `5882` confirms that `Rubberbanditz` in an EXERCISE_BAND Child title conflicts with `Brand = Generic`; remove the competitor brand from the title instead of changing the listing to that brand. The resulting `13013` offer error is downstream of the failed SKU creation.
- Always run the project template self-check before delivery when a filled template is produced, but do not generate or send self-check report files unless explicitly requested.
- The competitor-only batch fast-prelisting route is opt-in and isolated. Invoke it only when the user explicitly asks for `批量快速上品路线`, using `python3 run.py batch-fast-prelist <manifest.json>`. It reuses the existing writer and validator without changing `auto-fill`, keeps image fields blank, defaults to Haul Generic Variation, applies logistics tiers from `config/logistics_tiers.json`, isolates failures per task, and produces no reports by default. After writing, it evaluates the template's conditional-format formulas per populated Parent/Child row and blocks delivery when a currently triggered red-border field remains. A zero-red result is accepted only when every encountered formula is supported; unsupported formulas produce `needs_wps`, and new Product Types, template changes, or backend errors still require WPS/Excel fallback recalculation. When one saved competitor HTML contains a complete single `color_name` twister and the manifest does not explicitly provide `variants`, extract every color and generate one Parent plus all Children; never write competitor ASINs into the new template. Explicit `variants` take precedence, `expand_competitor_variants: false` opts out, and multi-dimension twisters require explicit variants. Read `docs/batch_fast_prelisting.md` for its manifest schema.
- Batch-fast fallback descriptions must remain four paragraphs and within the project 1500–1800 character range.
- Batch-fast manifests may use explicit `parent_extra_fields` for template-specific dynamic fields that the Parent row must also contain; ordinary `extra_fields` continue to apply only to Child rows.
- For batch-fast titles, when `base_title` is omitted, use the saved competitor page Product Title as the source, preserve its front and middle keyword order, and alter only 3–5 English words at the end by addition or deletion. An explicit `base_title` remains an override, and existing title length, restricted-term, and variation checks still apply. Do not change formal `auto-fill` title behavior.
- For that batch-fast route only, price precedence is explicit `price`, saved competitor HTML `priceToPay`, manually verified live Amazon `online_price`, then `estimated_price` only when both saved HTML and the live page have no current price. Never use discount amounts or prices from recommendation cards as the product price. When `copy_reference` is available, compare rows by SKU: keep `Create or Replace (Full Update)` for new SKUs, set the exact Valid Value `Edit (Partial Update)` only for existing SKUs whose fields changed, and do not change the action when no fields changed. Do not change the formal `auto-fill` action default.
- For batch-fast SKUs, tasks with `store_id = 1店` must use the `TTCA-` prefix for every Parent and Child SKU, including explicit SKU values; other stores default to `CA-`. After the prefix, take at most the first two English words from `product_name`, Title Case each word (first letter uppercase, remaining letters lowercase), concatenate the product words without an internal hyphen, and keep the variant suffix concise. Lowercase count and measurement unit tokens in the variant suffix, for example `TTCA-ToolSharpener-2pcs` and `TTCA-StorageHook-6mm`; keep ordinary attributes Title Case, for example `TTCA-GlassBeads-DarkGreen`. Outside `1店`, explicit `parent_sku`, `child_sku`, or variant `sku` remains an override. Do not change formal `auto-fill` SKU behavior.
- The batch-fast workbench keeps lightweight output version history per product. V1 is the normal current output; when Codex generates and synchronizes a corrected V2/V3, the highest version becomes current and earlier files remain available only as old-version downloads. The UI must not ask the user to upload output files or corrected versions; source-template upload remains user-facing. Do not store processing-summary reports in this workbench. Batch ZIP downloads include only each product's current latest output. The workbench includes a persistent `note` column; whenever a delivered output uses manifest `estimated_price`, set its note to the exact text `预估价格`.
- When a competitor variation is uncertain, do not silently classify or expand it. This includes a technical `color_name` twister whose buyer-facing option labels contain sizes/specifications, and any multi-dimension twister without explicit variants. Return `needs_variant_review`, set the workbench note to the exact text `变体主题待人工审核`, and require human confirmation of the theme and complete child set. Explicit manifest `variants` count as confirmation. If another note also applies, join notes with the Chinese semicolon `；`; an estimated-price-only note remains exactly `预估价格`.
- Batch-fast workbench business data is Git-shareable under `data/batch_fast_workbench/`. Ledger paths stored inside the repository must remain repository-relative. Before committing newly referenced external files, run `python3 run.py package-batch-workbench-data`; do not deliver or commit when it reports missing references. A colleague who pulls the same commit must be able to open the shared ledger and files without the original user's Desktop paths.
- The batch-fast workbench has three owner batches: `cady选品`, `图图选品`, and `凯旋选品`. Each has independent `1店` / `2店` views. Both stores under one owner share product links and competitor HTML, while source templates, current/old outputs, status, and notes are store-specific. For Cady, the historical populated data is under `2店` and the initially blank side is `1店`; for 图图 and 凯旋, historical data remains under `1店` and the initially blank side is `2店`.
- Cady `2店` additionally tracks a persistent procurement status immediately after listing status, with the exact values `已采购` and `未采购`. It is independent from the Amazon listing status and must survive ledger re-imports.
- The Amazon-reference batch workbench is displayed to users as `批量抄品工作台`; its internal `/batch-fast` route and batch-fast generation commands remain unchanged.
- The unified entry page is the default listing workbench at `/`. In its upper-left area, show only two compact switch links for `批量抄品工作台` and `退货翻新批量上品工作台`; do not present the three workbenches as equal parallel entry cards.
- The return/refurbishment batch workbench is isolated under `data/refurb_batch_workbench/`, is owned only by Cady, and always uses `1店`. Its UI route is `/refurb-batch`, its default source sheet is `退货翻新批量上品.xlsx`, and its source templates, output versions, statuses, and notes must not be mixed into the batch-copy ledger. In this workbench, the first table column shows the product name without a link, while the second column is named `亚马逊原链接` and contains the clickable original Amazon URL; the batch-copy workbench keeps its `竞品 HTML` column.
- Return/refurbishment image generation keeps the first Amazon gallery image as a scene-based main image: preserve the original product, use state, camera angle, and scene composition, and change only minor background, lighting, color, or framing details. Do not convert the main image to a white-background cutout. Auxiliary images remain faithful regenerations of their corresponding references.
- Return/refurbishment image groups are variant-aware. Ordinary single-link products keep one group; merged variation products keep one independent reference/generated set and ZIP per source child, labeled by its color, size, style, or set value; merged bundle products such as the four-piece tweezer set keep one combined group. Store new files under `image_groups/<group-key>/`, name images as product plus variant plus numeric order, and offer per-group downloads plus one all-groups ZIP after every variation group is complete. Continue reading legacy flat image fields so existing image sets are not lost.
- The refurb workbench exposes image work as two separate actions in every image-group card: `获取原产品图组` downloads and stores the Amazon gallery references without generating, then `生成新图组` becomes enabled and uses only the saved references. Re-fetching references invalidates the current generated ZIP in the ledger. Variation groups fetch from their own source child; merged bundle groups combine references from all retained source links into one group.
- The refurb workbench shows a live image-progress overview above the table, grouped into `未获取原图`, `已获取待生成`, `正在生成`, `生成失败` when applicable, and `已生成`, listing every product/variant in the appropriate bucket. While the page is visible and no form field is being edited, refresh this overview automatically every 15 seconds.
- The refurb image service reads `GRSAI_API_KEY` from the process environment first and falls back to the macOS Keychain generic-password service `shangpin-system-grsai-api-key`. Never persist the secret in source files, ledger data, shell history, or documentation.
- Every completed refurb image group offers `下载图组到桌面`, which copies the current generated image files directly without compression. Desktop exports are grouped in generation order under `~/Desktop/退货翻新新图组/本轮第NN批_进行中/<产品名-变体>/`; when a batch reaches 10 image groups, rename its container to `本轮第NN批_10组` and start the next batch. Re-downloading the same group refreshes its existing app-managed product folder even after batching. Do not expose per-group or all-groups ZIP download actions in the UI; retained ZIP data is internal compatibility state only.
- Newly generated refurb images must be normalized before they enter the ledger or desktop export: preserve the generated pixel dimensions, convert to non-transparent RGB JPEG with an sRGB profile at 72 dpi, require the longest side to stay within Amazon's 500–10,000 pixel range, and keep each file at or below 4.5 MB so the 5 MB uploader limit has a safety margin.
- In the refurb workbench, preserve every merged source Excel row, uploaded template, and Amazon original link inside the combined row. Confirmed groups are: `内裤-瑜伽` rows 12/14, `内裤-蕾丝` rows 15/19, and `内裤-蝴蝶` rows 22/25 as `SIZE`; gradient arm sleeves rows 50/51/52 as `COLOR`; masks as three separate `COLOR` families for rows 11/36, 37/39, and 38/40; and tweezers rows 53–56 as one four-piece bundle rather than a variation. Keep arm-sleeve rows 13 and 44 separate. Row 56 must be retained even though its source Amazon link duplicates row 55.
- The default workbench is a lightweight project record rather than the place for the full listing-generation conversation. Its left rail shows product name, upload status, a persistent product note, and a recoverable delete action that archives the project instead of permanently removing it. The main view has two sections: `资料确认` and `生成上传表`; the former keeps route selection, Amazon source template, 1688 detail page, SKU, selling price, and the first four configured delivery-fee options, while the latter records V1/V2/V3 files and per-version change notes. Do not restore a separate upload-result page unless the user explicitly asks.

If these instructions conflict with a direct user instruction in the current conversation, follow the user instruction, but explicitly call out the deviation from the project default.
